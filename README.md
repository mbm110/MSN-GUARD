## معرفی

**MSN-GUARD** یک کلاینت VPN بومی اندروید است که تمام ترافیک دستگاه را از طریق چهار ترابری مستقل تونل می‌کند. برخلاف اپ‌های پروکسی که فقط مرورگر را پوشش می‌دهند، این برنامه در سطح `VpnService` اندروید کار می‌کند: یک اینترفیس TUN می‌سازد و **همهٔ** بسته‌های TCP، UDP و QUIC کل گوشی — شامل اپ‌های دیگر — را از تونل عبور می‌دهد.

معماری آن دو لایه است: یک **هستهٔ شبکهٔ Rust** که خودش پروتکل‌ها را پیاده و مذاکره می‌کند، و یک **لایهٔ Kotlin** که چرخهٔ حیات VPN، رابط کاربری و یکپارچگی با پلتفرم را در دست دارد. هیچ سرور واسطی در میان نیست؛ کلاینت مستقیماً با گیت‌وی‌های بالادست حرف می‌زند.

> این برنامه با تمرکز بر شبکه‌های ایران توسعه یافته است: هر تصمیم پروتکلی در آن نتیجهٔ **اندازه‌گیری واقعی روی اپراتورهای همراه اول، ایرانسل و سامان‌تل** است، نه حدس.

## قابلیت‌ها در یک نگاه

| | |
|---|---|
| **تونل کل دستگاه** | `VpnService` + TUN با MTU ۱۵۰۰؛ تمام اپ‌ها بدون تنظیم اضافه پوشش داده می‌شوند |
| **چهار ترابری** | MASQUE (HTTP/3)، WireGuard، WARP-on-WARP، Psiphon |
| **اتصال یک‌کلیکی** | یک دکمه؛ انتخاب گیت‌وی، مذاکره و بازیابی همه خودکار |
| **پشتیبانی کامل UDP/QUIC** | از طریق `udpgw` — ویدیو، بازی و تماس صوتی کار می‌کنند |
| **نمایش زندهٔ وضعیت** | IP خروجی + پرچم کشور، مصرف داده، مدت اتصال، لاگ لحظه‌ای |
| **کاشی تنظیمات سریع** | اتصال/قطع از Quick Settings بدون باز کردن برنامه |
| **Split Tunneling بومی** | انتخاب اپ‌هایی که باید بیرون از تونل بمانند |
| **Kill Switch** | قطع کامل شبکه در صورت افتادن تونل |
| **DNS اجباری** | استفادهٔ اجباری از resolver عمومی و حذف DNS اپراتور |

## معماری

```text
┌──────────────────────────────────────────────────────────────┐
│                    لایهٔ Kotlin  (اندروید)                    │
│                                                              │
│  MainActivity        رابط کاربری، کنسول اتصال، تنظیمات        │
│  MsnGuardVpnService  چرخهٔ حیات VPN، TUN، نردبان Psiphon      │
│  MsnGuardTileService کاشی تنظیمات سریع                        │
│  Tun2SocksManager    مدیریت tun2socks بومی                    │
└───────────────────────────┬──────────────────────────────────┘
                            │  JNI  (aether_jni.cpp)
┌───────────────────────────▼──────────────────────────────────┐
│                  هستهٔ Rust  →  libaether.so                  │
│                                                              │
│  prober.rs     کشف و رتبه‌بندی گیت‌وی‌ها                       │
│  account.rs    ثبت‌نام دستگاه، صدور گواهی MASQUE              │
│  quic.rs       ترابری QUIC / HTTP-3                          │
│  masque.rs     کپسوله‌سازی CONNECT-IP                        │
│  wireguard.rs  Noise handshake و ترابری WireGuard            │
│  netstack.rs   پل بستهٔ سطح TUN                              │
└──────────────────────────────────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│              لایهٔ C بومی  (پردازش بسته)                       │
│  badvpn tun2socks + lwIP  —  TCP/IP در فضای کاربر            │
│  udpgw  —  انتقال دیتاگرام UDP/QUIC روی ۱۲۷.۰.۰.۱:۷۳۰۰      │
└──────────────────────────────────────────────────────────────┘
```

مسیر دادهٔ یک بستهٔ خروجی: اپ کاربر → TUN → tun2socks/lwIP → SOCKS محلی → هستهٔ Rust → ترابری رمزنگاری‌شده → گیت‌وی → اینترنت.

## ترابری‌ها

### MASQUE روی HTTP/3

پیاده‌سازی `CONNECT-IP` روی QUIC، مبتنی بر کتابخانهٔ [quiche](https://github.com/cloudflare/quiche). این ترابری از نظر شبکه از یک اتصال HTTPS معمولی قابل تفکیک نیست.

جزئیاتی که با اندازه‌گیری واقعی به دست آمد و در کد مستند شده است:

- هدر شبه‌استاندارد باید `:protocol = cf-connect-ip` باشد. مقدار استاندارد `connect-ip` پاسخ `403` می‌گیرد.
- **HTTP/2 برای این کار مرده است**: کلادفلر `SETTINGS_ENABLE_CONNECT_PROTOCOL` را روی HTTP/2 اعلام نمی‌کند، پس extended CONNECT همیشه `400` برمی‌گرداند. تنها HTTP/3 کار می‌کند.
- ترتیب گیت‌وی‌های seed **اندازه‌گیری‌شده است، نه حدسی**: از هشت آدرس شناخته‌شده تنها `162.159.198.2` و `162.159.198.1` پاسخ `200` می‌دهند؛ `162.159.196.1`، `195.1` و `192.1` دست‌دهی QUIC را رد می‌کنند.
- گیت‌وی تخصیص‌یافته از پاسخ enrollment کلید MASQUE خوانده می‌شود، نه از ثبت‌نام WireGuard.

### WireGuard

ترابری مستقیم با Noise handshake کامل، برای شبکه‌هایی که UDP را مسدود نکرده‌اند. سریع‌ترین گزینه در جایی که کار کند.

### WARP-on-WARP

تونل WireGuard تونل‌شده در WireGuard. مسیر بیرونی باید در دسترس باشد.

### Psiphon — نردبان سه‌پله‌ای

پله‌ها **بر اساس زمانِ اندازه‌گیری‌شدهٔ اتصال روی اپراتور خصمانه** مرتب شده‌اند، نه بر اساس ترتیب پیش‌فرض Psiphon:

| پله | راهبرد | بودجه | چرا این ترتیب |
|---|---|---|---|
| **A** | domain-fronted (CDN) | ۶۰ ثانیه | تنها مسیری که روی همراه اول کار می‌کند؛ لبهٔ CDN را می‌زند نه IP سرور Psiphon |
| **D** | همهٔ پروتکل‌ها (مستقیم) | ۴۵ ثانیه | برندهٔ سریع روی اپراتوری که چیزی مسدود نکرده (سامان‌تل: QUIC-OSSH در چند ثانیه) |
| **C** | in-proxy (رلهٔ کاربران) | ۷۵ ثانیه | آخرین راه‌حل؛ آدرس‌های خانگی که در لیست سیاه اپراتور نیستند |

روی همراه اول هر دیال مستقیم در **لایهٔ TCP** شکست می‌خورد — نه reset، نه خطای TLS، بسته‌ها هرگز نمی‌رسند. اپراتور IP سرورهای Psiphon را null-route می‌کند. تنها ۵ مورد از ۴۳۰ ورودی سرور بستهٔ Psiphon پروتکل FRONTED-MEEK را اعلام می‌کنند، و همین دلیل قرار گرفتن پلهٔ A در صدر است. پلهٔ برنده برای هر سیم‌کارت ذخیره می‌شود، پس بعد از یک اتصال موفق، دستگاه از بهترین پلهٔ خودش شروع می‌کند.

## جزئیات فنی که اهمیت دارند

**حلقهٔ مسیریابی.** فرایند Psiphon خودش باید بیرون از تونل بماند، وگرنه ترافیکش به TUN برمی‌گردد و حلقه می‌سازد. با `addDisallowedApplication(packageName)` روی بستهٔ خودمان حل شده است.

**UDP و QUIC.** پشتهٔ lwIP فقط TCP را ترمینیت می‌کند. دیتاگرام‌ها از طریق `udpgw` روی `127.0.0.1:7300` با ظرفیت ۱۲۸ اتصال همزمان منتقل می‌شوند — بدون این، QUIC و بازی‌های آنلاین کار نمی‌کنند.

**MTU.** روی ۱۵۰۰ ثابت است. مقادیر کوچک‌تر باعث تکه‌تکه شدن و افت محسوس throughput روی مسیر MASQUE می‌شد.

**پورت SOCKS.** روی `127.0.0.1:1819` ثابت و غیرقابل تغییر است. در حالت VPN هیچ‌چیز بیرونی به آن بایند نمی‌شود، پس قابل تنظیم بودنش فقط سطح خطا اضافه می‌کرد.

**تشخیص رد هویتی.** فقط `401` و `403` رد هویتی حساب می‌شوند. `400` یعنی درخواست بدشکل — اشتباه گرفتن این دو باعث می‌شد ثبت‌نام سالم دور ریخته شود.

**آدرس‌دهی.** TUN روی `10.0.0.1/8`، روتر `10.0.0.2`، DNS اجباری روی resolver عمومی با حذف کامل DNS اپراتور.

## نصب

آخرین APK از [بخش Releases](https://github.com/mbm110/MSN-GUARD/releases) یا از artifact های [Actions](https://github.com/mbm110/MSN-GUARD/actions) قابل دریافت است.

| معماری دستگاه | فایل |
|---|---|
| ARM ۶۴ بیتی (اکثر گوشی‌های امروزی) | `app-arm64-v8a-debug.apk` |
| ARM ۳۲ بیتی (دستگاه‌های قدیمی‌تر) | `app-armeabi-v7a-debug.apk` |

حداقل نسخهٔ اندروید: **۸.۰ (API 26)**. هنگام نصب، اجازهٔ نصب از منبع نامشخص را بدهید و در اولین اتصال، درخواست مجوز VPN اندروید را تأیید کنید.

## ساخت از سورس

**پیش‌نیازها:** JDK 17 · Android SDK 36 · NDK `26.3.11579264` · CMake `3.22.1` · Rust stable + هدف‌های اندروید · `cargo-ndk`

```bash
rustup target add aarch64-linux-android armv7-linux-androideabi
cargo install cargo-ndk

./gradlew assembleDebug -PtargetAbi=arm64-v8a,armeabi-v7a
```

خروجی در `app/build/outputs/apk/debug/` قرار می‌گیرد. اسکریپت `core/build-android.sh` هستهٔ Rust را برای هر ABI کامپایل و `libaether.so` را در محل درست قرار می‌دهد؛ Gradle خودش آن را صدا می‌زند.

هر push روی شاخهٔ `master` گردش‌کار [`build.yml`](.github/workflows/build.yml) را اجرا می‌کند و APK هر دو معماری را به‌عنوان artifact آپلود می‌کند.

## ساختار پروژه

```text
app/
  src/main/java/…/          کلاینت Kotlin  (۵٬۹۶۲ خط)
  src/main/cpp/
    aether_jni.cpp          پل JNI بین Kotlin و هستهٔ Rust
    badvpn/                 tun2socks + lwIP  (وندور شده)
core/
  aether/src/               هستهٔ شبکهٔ Rust  (۳۲ فایل)
  quiche/                   کتابخانهٔ QUIC/HTTP-3 کلادفلر  (وندور شده)
.github/workflows/          گردش‌کار ساخت CI
docs/                       مستندات و دارایی‌های برند
```

آمار زبان‌های مخزن با `.gitattributes` تصحیح شده است: `core/quiche` و `badvpn` به‌عنوان vendored علامت‌گذاری شده‌اند تا نوار زبان‌ها **کدی را که نوشته شده** نشان دهد — Rust و Kotlin — نه ۷.۶ مگابایت کتابخانهٔ ثالثی که برای ساخت لازم است.
