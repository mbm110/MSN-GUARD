# Lantern transport prototype

This document describes the isolated Lantern prototype on
`feature/lantern-prototype`. It is not a release-readiness claim.

## Design

The app remains the only owner of Android's `VpnService` and device TUN.
Radiance is compiled with its `novpn` build tag, which replaces its normal TUN
inbound with a loopback-only mixed HTTP/SOCKS listener:

```text
Android applications
        |
MSN-GUARD VpnService + TUN
        |
existing Hev engine
        |
127.0.0.1:1831 (Radiance mixed SOCKS/HTTP inbound)
        |
Radiance / Lantern public server selection
        |
public internet
```

The app UID is excluded from its own TUN by the existing split-tunnel builder,
so Radiance's upstream sockets do not recurse into the tunnel. The listener is
bound to loopback only. No Lantern listener is published to the LAN.

## Build

The nested Go module pins Radiance to a fixed upstream commit. The Android AAR
is generated by `core/lanternbridge/build-android.sh`; it is not checked into
the repository. The script pins the Go mobile binding tool and builds the
`arm`, `arm64`, and `amd64` Android targets.

Required build components:

- Go 1.26.10
- Android SDK platforms 26 and 36
- Android NDK 26.3.11579264
- CMake 3.22.1
- Java 21 for the Gradle build

The app's `preBuild` task generates the AAR before Kotlin compilation.

## Scope and safeguards

- Lantern is an eighth transport; the seven existing transport engines and
  their transport-specific implementation files are not edited.
- Lantern is VPN-mode only. Proxy-only mode and LAN proxy sharing are refused.
- Radiance telemetry consent is set to false in the bridge options.
- Radiance data and logs live in the app-private
  `files/lantern-radiance/` directory.
- The Go bridge uses Radiance's automatic server selector and does not ask for
  a private server access key.
- The bridge has its own SOCKS port (1831), distinct from the existing
  transport ports.

## Required validation before merge or release

1. GitHub Actions must compile the Go bridge and all Android ABIs.
2. Confirm the produced AAR contains only the intended Android ABIs and review
   its compressed and uncompressed size.
3. Install on API 26 and a current Android release.
4. Connect through a public Lantern server; verify TCP, UDP, DNS, IPv4, and
   IPv6 using actual traffic through the TUN, not only a connected status.
5. Check that the Radiance listener binds only to 127.0.0.1:1831.
6. Verify no second `VpnService` is started and no traffic leaks around the
   TUN, including IPv6 and DNS.
7. Test connect, disconnect, reconnect, timeout, network changes, sleep/wake,
   and force-stop/restart.
8. Run regression tests for WireGuard, MASQUE, WoW, Psiphon, Tor, Foxy, and
   SHARD on the same device and verify traffic, DNS, IPv6, and teardown.
9. Review the full transitive dependency license inventory and include the
   required third-party notices in distributed APKs.

Do not merge this prototype until the build and device tests above pass.
